# OarbankLease: a TLA+ model of oarbankd's lease, fencing and acceptance protocol

`OarbankLease.tla` models the coordinator (`src/oarbank/coordinator/core.py`) and its agents at
commit **bb04f9d**. That commit and 5ed1465 fix all six defects this model found (F1–F6, see
**Findings**). The model covers leases, generation and certification fencing, idempotent
completions over a lossy network, late completions, quorum disputes, self-inconsistency
conviction, adaptive replication, quarantine with result invalidation, module revocation,
certification with a grace period and a golden-failure limit, coordinator crashes, and user
retry/cancel.

TLC checks it under 57 configurations (54 plus the three module-fault configurations):

* **The code as written** (every switch at its bb04f9d value) satisfies properties 1–5, I1
  (`NoHonestConviction`), I2, every other safety property, and liveness. That includes the
  2-node and 3-node double-vote scopes, a consistently wrong faulty node, golden jobs that stall
  forever, and golden jobs that always fail.
* **Every weakened variant fails** the property it is meant to break. (a)–(d) remove core rules;
  (e)–(n) put back an older behaviour (commit named), including every pre-fix defect that is
  inside the model (F1–F3, F5, F6; F4 concerns golden-job dispatch, which is not modelled).
* **No new defects.** The replays against the real `core.py` agree with the model.

```sh
./run_tlc.sh                 # everything (about 22 minutes on an M4 Max)
QUICK=1 ./run_tlc.sh         # skip the four slowest configurations (about 9 minutes)
./run_tlc.sh double_vote     # only configurations whose name contains "double_vote"
```

## The model

### State

| TLA+ variable | core.py / agent state |
|---------------|-----------------------|
| `job[j]` = `[st, g, canon, fails, disp, dres]` | `jobs.state` (`absent` = replica job not created yet), `generation`, `canonical_result_id` (as an attempt id), `exec_failures`, `dispute_json.nodes`, `dispute_json.results` |
| `att[a]` = `[j, n, g, cg, st, rv, racc, rcan]` | one `attempts` row joined with its `results` row (`results.attempt_id` is UNIQUE): `job_id`, `node_id`, `generation`, `cert_generation`, `state`, result value, `results.accepted`, `results.canonical` |
| `nextAtt` | `attempts.attempt_id` AUTOINCREMENT |
| `cert[n]`, `cfy[n]` | `modules_json[m]`: `generation` (negative = revoked or `golden_failed`; core.py writes -1) and `state = 'certifying'` |
| `gold[n]` | `modules_json[m]`: `state = 'golden_failed'` (`gfd`), `golden_failures` (`gfail`), CERTIFYING_GRACE_S passed since `certifying_since` (`graceOver`); pending golden sets (`sets`); history: golden failures since the last certification or `golden_failed` (`gcons`) |
| `brk[n]` | a module left in `state='revoked'` with its generation kept (the pre-27aa459 breaker; FALSE in the code as written) |
| `quar[n]` | `nodes.lifecycle = 'quarantined'` |
| `up`, `snap`, `inflight` | coordinator process up; volatile: the node row an in-progress claim read in `auth_node` (variant h only); completions past a non-transactional idempotency check (variant d only) |
| `running[n]`, `asleep[n]` | agent: attempt processes running, the machine asleep |
| `outbox`, `net` | agent outboxes (durable) and in-flight messages |
| `faults`, `userOps` | fault and user-operation budgets |
| `ghost` | history variables for properties 3, 5 and the extras |

Jobs are eval jobs, plus (in some configurations) a replica job that `_maybe_replicate` creates
when its target eval job gets a canonical result. The one module is implicit. Result values are
`"A"` (correct) and `"B"`. Only nodes in `FaultyNodes` can produce `"B"`: at random, or always
when `FaultyAlwaysWrong = TRUE`.

### Abstractions

* **Transactions are atomic steps.** Each core.py function runs inside one `with db.tx()`
  (`BEGIN IMMEDIATE` under a process-wide lock) and its `post` callbacks run before the commit,
  so each is one TLA+ action. The pre-5ed1465 `claim` is two actions (variant h).
* **Time is abstract.** `ReapOrphan(a)` (fair, free) expires a live lease that nobody renews:
  the agent does not run the attempt (grant lost, attempt finished or released) or is asleep.
  `Expire(a)` (a counted fault) expires any other live lease: lost heartbeats, a stall, a restart
  outage. Lease extension on heartbeat or restart is therefore a no-op: any lease may expire at
  any time, within the fault budget.
* **Network.** Agent reports (`complete`, `release`, `fail`) sit in a durable outbox and are
  (re)sent into `net`, a set, so messages are reordered and delayed. A message can be dropped;
  a processed request's response can be lost, and the agent then re-sends the same report, which
  models duplicates. Grant responses and heartbeat revoke lists can be lost as well.
* **Bounded faults.** Drop, lost response, lost grant, spurious expiry, sleep, agent release,
  execution failure, coordinator crash, golden-mismatch revocation and operator quarantine each
  spend one unit of `MaxFaults`; `retry_job`/`cancel_job` spend `MaxUserOps`. Attempt ids are
  bounded by `MaxAtt`. The bounds keep the state space finite and make "eventually reliable
  delivery" a consequence of weak fairness.
* **Certification.** After a revocation the node doctors and queues goldens (`BeginCertify`,
  fair) and is `certifying`. Its golden set then passes (`Recertify`, fair unless
  `CertifyMayStall` or the node is in `GoldenFailNodes`), fails (`GoldenFail`, fair for
  `GoldenFailNodes`, a counted fault for others; `trip` = the node breaker trips), or neither.
  CERTIFYING_GRACE_S passing is `GraceExpires` (fair), and RECERT_EVERY passing for a
  `golden_failed` module is `RetryGoldenFailed` (fair). Golden jobs are not modelled as jobs.
* **Reaper fairness.** The replica cancel and the stranded-dispute check get strong fairness. The
  reaper runs every REAPER_EVERY seconds, and with a failing node that is retried every
  RECERT_EVERY, their conditions hold only intermittently (while the node is `golden_failed`),
  for hours at a time.
* **Not modelled:** golden jobs as jobs, studies and trials, resource fitting and caps, hard deadlines,
  heartbeat progress accounting, enrollment, releases, `hello` reconciliation (covered by
  `Expire`), backoff timers, multiple modules.

### Properties

| # | TLA+ name | statement |
|---|-----------|-----------|
| 1 | `OneCanonical` | at most one canonical result per job at any time |
| 2 | `CanonicalGenCurrent` | a canonical result's attempt generation equals the job's generation |
| 3 | `StaleNeverCanonical` | a completion whose generation differs from the job's at acceptance time is never made canonical (history variable) |
| 4 | `NoLostJob` | every leased job has a live attempt (so a job whose attempts all ended is pending or settled), and every live attempt belongs to a leased job of its own generation |
| 5 | `QuarantinedNoGrant` | a quarantined node never receives a grant (history variable) |
| S2 | `DoneHasCanonical` | a done job's `canonical_result_id` points at a canonical result of that job |
| S7/S8 | `LiveOnReadyCertified` | live attempts run only on non-quarantined nodes, under the node's current certification |
| — | `NoCanonicalFromQuarantined` | no result from a node that is quarantined at acceptance becomes canonical |
| — | `NoCanonicalFromUncertified` | no result becomes canonical while its node's module is revoked |
| — | `SettledNotRevived` | an accepted completion never lands on a cancelled or quarantined job (only `retry_job` reopens it) |
| I1 | `NoHonestConviction` | a correct node is never convicted of nondeterminism (every configuration has exactly one faulty node, so a quorum of distinct nodes can never outvote a correct one) |
| I2 | `ConvictedResultsInvalidated` | once a node is convicted, no canonical eval result it produced survives |
| F6 | `GoldenSetsBounded` | a module never has more than one pending golden set |
| F6 | `GoldenFailuresBounded` | at most MAX_EXEC_FAILURES golden failures on a node before it is certified or taken out of service as `golden_failed` (with an alert) |
| L | `Liveness` | `(\E n : [](~quar[n]) /\ <>[](Certified(n))) => \A j : <>[](job[j].st \in {done, cancelled, quarantined} \/ never created)` |

**Liveness assumptions** (`Fairness` in the spec): weak fairness on delivery with a response, on
each agent's claims, on `ReapOrphan`, on doctoring, on recertification (unless
`CertifyMayStall`), on golden failure for `GoldenFailNodes` (unless `CertifyMayStall`), on the
grace period and RECERT_EVERY passing, on coordinator restart, and on the agent finishing,
sending and waking. `ReapReplica` and `ReapStranded` get strong fairness (see Abstractions). All faults and user operations are
unfair and bounded, so after the last fault every message that keeps being re-sent is
delivered. The hypothesis "some node is never quarantined and ends up certified" is needed
because `clear_quarantine` is an operator action outside the model. "Quarantined" counts as
settled: a job reaches it through the failure policy or when a dispute cannot be broken.

The `OarbankLease_witness_*` configurations are vacuity checks. Each states that some scenario
never happens and TLC must find a trace where it does: a late completion wins, a dispute opens,
a tie-break convicts, a stranded dispute is quarantined, a replica disagrees, the reaper cancels
a replica, a node convicts itself, a party's late vote is fenced, a stale completion is rejected,
a retried job completes again, a revoked module's result is rejected, a node goes
`golden_failed`, and a certifying node's grace expires and the reaper cancels a replica.

## Weakened variants

Each variant removes one rule, or puts back an older behaviour, and TLC finds a counterexample,
so each rule is load-bearing. The traces are summarized from `out/<config>.log`; `a1, a2, ...`
are attempt ids, n2 (or n3 on 3 nodes) is the faulty node.

### (a)–(d): core rules removed

**(a) No generation fence** (`Variant = "nofence"`). `StaleNeverCanonical` is violated after
12 states. n1's a2 for j2 expires while n1 keeps running it; n1 gets a3 for j2; a3 is canonical;
the user retries j2 (generation 2); a2's late generation-1 result is then made canonical for
generation 2.

**(b) Reaper does not return the job** (`Variant = "noreturn"`). `NoLostJob` is violated after
4 states: a grant response is lost, nobody renews the lease, the reaper expires it, and the job
stays leased with no live attempt. `_b_noreturn_liveness` shows the consequence (9 states): after a
retry the new attempt's lease expires, and the job stays leased with no live attempt forever.

**(c) Retry without demotion** (`Variant = "nodemote"`). `CanonicalGenCurrent` is violated
right after the retry (9 states): j2's generation-1 result is still canonical in generation 2.
With only `OneCanonical` checked (`_c_nodemote_one`, 13 states), j1's generation-2 result becomes
canonical as well, and j1 has two canonical results.

**(d) Idempotency check outside the transaction** (`Variant = "nonatomic"`). `DoneHasCanonical`
is violated after 12 states: the agent re-sends a slow completion, two handler threads both pass
the lookup, the first commits the result as canonical, and the second re-processes it as a late
replica of the done job and rewrites the row as `accepted=0`. (Real SQLite would fail the second
insert on `UNIQUE(attempt_id)` with a 500 instead.)

### (e)–(g): fixed by 27aa459 and 8e5abc6

**(e) No quarantine fence** (pre-8e5abc6). `NoCanonicalFromQuarantined`, 7 states: n1's a1
expires while n1 keeps running it, an operator quarantines n1, and a1's result becomes canonical.

**(f) Breaker keeps the generation** (pre-27aa459). `LiveOnReadyCertified`, 7 states: the
breaker marks the module revoked while another attempt of the node stays live under the old
cert generation. `_canon` (10 states): that attempt's result becomes canonical from a revoked
module.

**(g) Strict `failed_here`** (pre-8e5abc6). Liveness, 7 states: n2 fails j1 once and n1 is
quarantined; n2 is then excluded from j1 forever and j1 never settles.

### (h)–(l): fixed by 5ed1465 (findings F1–F3)

**(h) Claim trusts the auth snapshot** (finding F1). `QuarantinedNoGrant`, 4 states: n1's claim
passes auth, an operator quarantines n1, and the claim transaction grants j1 to n1.
`_h_claim_snapshot_revoked` (4 states): the same race with `revoke_module`; the attempt carries
the old cert generation of a revoked module (`LiveOnReadyCertified`).

**(i) Pre-5ed1465 dispute handling** (finding F2: no party fence, no generation bump, no
settled-job fence, no self-inconsistency rule). `NoHonestConviction`, 15 states on 2 nodes, on 3
nodes, and with a consistently wrong faulty node. The 3-node always-wrong trace: n1's a1 expires;
n3 gets a2, which expires; n3 gets a3; a3 = B is canonical; n1's late a1 = A opens a dispute
{n1, n3}; n3's late a2 = B is counted as the tie-break vote, agrees with a3, and **n1, the correct
node, is convicted**.

Which of the four 5ed1465 dispute rules are needed? Removing them one at a time:

| config | removed | result |
|--------|---------|--------|
| `_i1_party_fence_only` | the generation bump | every property holds: the `dispute_party` fence alone stops the double vote |
| `_i2_gen_bump_only` | the `dispute_party` fence | every property holds: after the bump the party's older attempt is fenced as `stale_generation`, and `claim()` already keeps parties from new attempts |
| `_i3_no_self_inconsistency` | the self-inconsistency conviction | every property holds: a node that disagrees with itself is caught by the ordinary dispute and tie-break, just later |
| `_k_no_settled_fence` | the `job_<state>` fence | `SettledNotRevived` fails (below) |

So the party fence and the generation bump each suffice for I1 (defence in depth), and the
self-inconsistency rule speeds up conviction but is not needed for any modelled property.

**(k) No settled-job fence** (pre-5ed1465). `SettledNotRevived`, 14 states (execution failures,
`MAX_EXEC_FAILURES = 2`, 3 faults): n1's a1 expires while n1 keeps running it; a2 on n1 and a3 on
n2 both fail; j1 is quarantined by the failure policy; a1's late result is accepted and revives
the quarantined job as done.

**(l) Pre-5ed1465 replication** (finding F3: no eligibility check, no reaper cancel). Liveness,
8 states: n1 is quarantined, n2's result for j1 is canonical, the replica excludes n2, and the
replica never settles. Removing the two 5ed1465 rules one at a time:
`_l1_reap_cancel_only` holds (the reaper cancel alone suffices), but `_l2_eligible_check_only`
fails liveness in 8 states. The replica is created (excluding n1) while n2 is eligible, then n2
is quarantined, and without the reaper cancel nothing settles it. The creation-time check alone is not enough;
the reaper cancel is the load-bearing half.

### (m), (n): fixed by bb04f9d (findings F5, F6)

**(m) A certifying node counts as eligible forever** (finding F5; `CertifyingGrace = FALSE`, golden
jobs may stall). Liveness is violated in two ways:
* `_m_replica_behind_stalled_certifying`, 10 states: n2 is revoked and stuck `certifying` (its
  grace period has even expired); n1's result for j1 is canonical and a replica is created,
  excluding n1. n2 still counts as eligible, so the reaper never cancels the replica, and n2 can
  never claim it.
* `_m_dispute_behind_stalled_certifying`, 14 states, 3 nodes: a 2-party dispute whose only
  possible tie-breaker is stuck `certifying` is never declared stranded.

With the grace period (the code as written), both scopes satisfy liveness
(`_stalled_goldens_liveness`, `_stalled_goldens_dispute_liveness`).

**(n) No golden failure limit** (finding F6; `GoldenFailLimit = FALSE`; n2's golden jobs always
fail):
* `GoldenSetsBounded` is violated in 5 states. n1's module is revoked and it queues goldens;
  one golden fails and trips the breaker, which revokes the module, and the next doctor pass
  queues a second set while the first is still pending.
* `GoldenFailuresBounded` is violated in 8 states: n2 fails four goldens in a row and is never
  taken out of service.

With the limit (the code as written), `_failing_goldens` and `_failing_goldens_liveness` hold:
n2 cycles `certifying` → `golden_failed` → (RECERT_EVERY) → `certifying`, never has more than one
golden set, never fails more than three goldens per cycle, and every job still settles.

### (o): module faults (S15)

Module code runs out of process, and a completion needs the module's verdict (`result.evaluate`) before oarbankd's transaction.

The model adds:

- **`modUp`:** whether the module host can evaluate. It goes down through `ModuleDown`, which counts against the fault budget, and recovers through `ModuleUp`, which is fair.
- **`DeliverModuleDown`:** a first completion delivered while the module is down gets a 503. The report stays in the agent's outbox, and the attempt is marked `aw`, the model's `attempts.phase = 'awaiting_module'`.
- **Code behaviour (`AwaitHoldsLease = TRUE`):** an awaiting attempt is `Held`. Neither `ReapOrphan` nor `Expire` ends it, because `core._await_module` extends its lease on every redelivery and the reaper exempts it from the hard deadline.
- **Property `ModuleFaultsNotCharged` (S15):** no attempt that waited on its module is ever expired.

| Config | Expected | What it shows |
|---|---|---|
| `OarbankLease_module_faults` | ok | Module outages break no safety property, S15 included. |
| `OarbankLease_module_faults_liveness` | ok | Every job still settles once the module is back. |
| `OarbankLease_o_no_await_lease` | `inv:ModuleFaultsNotCharged` | Without the lease hold, a finished attempt waiting on its module lapses. It is expired and re-run, which charges the job for a module fault. TLC finds this in 7 steps. |

fix, with a throwaway script outside the repo that calls the core functions on a temporary

### Replays

**F1** (59f4598): a node dict read before `quarantine()`, then `claim()` → 2 grants to the
quarantined node. At 5ed1465 the core tests pin the fix (`test_F1_*`).

**F2** (59f4598 → 5ed1465): the TLC order of calls on 2 and 3 certified nodes. At 59f4598:
`a3 ok, a2 disputed, a1 ok`; n1 (correct) `quarantined`; the canonical score is the wrong
0.860000 from n2. At 5ed1465: `a3 ok, a2 disputed, a1 dispute_party`; both nodes stay `ready`;
`invariants.check_all` reports nothing.

**F3** (59f4598): `replica_rate = 1`, n1 quarantined, n2 drains the queue → the replica jobs stay
`pending` for good. At 5ed1465 the core tests pin the fix (`test_F3_*`).

**F4** (59f4598): a golden job that fails once with `exit_nonzero` stays `pending` and is never
re-granted; the module stays `certifying`. Fixed in 5ed1465 (`test_F4_*`), which exposed F6.

**F5** (5ed1465 → bb04f9d). n2 is stuck `certifying` and a replica of n1's job exists:
* at 5ed1465 the replica is still `pending` after 20 reaper rounds (about 4 simulated hours);
* at bb04f9d, with n2's golden job stalling (claimed, never reported, lease expiring), the replica
  is `pending` for the first 25 minutes and `cancelled` from minute 30, when CERTIFYING_GRACE_S
  runs out.

The 3-node dispute whose only tie-breaker keeps failing its goldens is `pending` indefinitely at
5ed1465. At bb04f9d the tie-breaker goes `golden_failed`, the dispute is declared stranded, and the
job is `quarantined`. The stalled-golden variant of that dispute was checked in the model only
(`_stalled_goldens_dispute_liveness`).

**F6** (5ed1465 → bb04f9d). A node whose golden job for one module always exits non-zero:
* at 5ed1465, 12 rounds gave 48 failures, 10 pending golden jobs, and a module that stayed
  `certifying`;
* at bb04f9d, the 3rd failure gives `golden_failed` with one alert; its golden job is
  `cancelled` and none are pending.

Over 26 simulated hours the module cycles `certified`, `golden_failed` for 6 h, then retries:
9 failures in total, one open alert, never more than one golden set, and `invariants.check_all`
clean. (The first hours show `certified` because the node started out certified before its
goldens began to fail.)

### Remaining observations (not defects)

* **A node whose golden jobs never finish stays `certifying` with no alert.** This happens only
  when its golden leases keep expiring (for example, an agent that sleeps through every run),
  because lease expiry is not a failure. A hung golden job is still killed at `hard_deadline` and
  counted as a golden failure, so it reaches `golden_failed`. Since bb04f9d such a node blocks
  nothing (F5), but it is invisible to the operator. An alert when `certifying` outlasts
  CERTIFYING_GRACE_S would close that gap.
* **`_check_replica` compares against the original's *current* canonical result.** If the user
  retried the original after the replica was created, the two results can come from the same
  node, and the result is a one-party dispute rather than an immediate self-inconsistency
  conviction. It resolves correctly, just later.

## Limitations

* **Small scopes.** The checks are exhaustive only within their bounds: 2 or 3 nodes, 1 or 2
  jobs (plus one replica job), 4 to 6 attempt ids, 1 to 3 faults (a transient golden failure
  is one), and at most one user operation. That is enough for every counterexample here; the longest has 15 states.
  A scenario that needs more independent faults than the budget would be missed.
* **Liveness scopes are smaller still** (1 job, no symmetry reduction; the replica liveness
  configurations drop user operations). The attempt-id bound is a model artifact. A liveness
  violation that turns out to be "no attempt ids left" is not a finding, and the liveness
  configurations are sized to avoid it.
* **One module, abstract results.** Results are A/B. `validate_result`, mode mismatch, objective
  values and the bench module's "no value comparison" rule are abstracted away. Golden jobs,
  doctor runs, releases, resources, caps, studies/trials, hard deadlines and backoff timers are
  not modelled. Golden jobs are a per-node outcome (pass, fail, stall), so golden-job dispatch
  (F4) is checked only by the replays.
* **Time.** Lease timing and lease extension (heartbeat progress, the post-restart extension in
  `__main__`) are replaced by "any lease may expire" within the fault budget. The model says
  nothing about how *often* spurious expiry happens, only what it can break.
* **The agent** is abstracted to its protocol-visible behaviour: outbox with retries, grants,
  heartbeat kill lists, sleep. It does not model agent crashes that lose running processes
  (covered by a lost grant plus `ReapOrphan`) or `hello` reconciliation.
* **SQLite** is assumed to give serializable transactions (`BEGIN IMMEDIATE` under one process
  lock) and durable commits (`synchronous=FULL`).
* **The model tracks core.py at bb04f9d.** Re-run `./run_tlc.sh` after protocol changes and
  update the matching action (the table above names the lines).
